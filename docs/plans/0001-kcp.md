# PLAN 0001 - kcp as the state engine for spec driven development

Status: active. Owner: coordination agent. Executors: headless `deepseek-claude -p`.

## Objective

kcp (Kubernetes control plane, no nodes) is built to manage state. This repo
(`github.com/publicdomainrelay/graph-clm-kcp-spec`) builds a **two way state
sync** for spec driven development:

```
            code -> spec  (ingest, summarize, drift)
  git repo  ------------------------------------------>  kcp (CRs = specs)
  (code)    <------------------------------------------  (desired state)
            spec -> code  (realize: agent edits code, tests gate)

                 both directions index into the graph DB (HydraDB, Bolt)
                 and are driven by a context language model (CLM) loop
```

- **kcp** holds specs as custom resources. `spec` is the desired state of a
  part of the system. `status` is what the code is observed to be. A spec edit
  is a desired-state change; a reconciler drives the code to it, exactly like a
  Deployment drives pods.
- **Graph DB** (HydraDB over Bolt, ArcadeDB as alternate) indexes specs,
  requirements and code references (CodeGraph ids) so a model gets a small,
  relevant neighborhood instead of a 3000 line document.
- **Context language model** (CLM, as in `pi-hydradb-clm/`): each spec has a
  context document the model reads and edits. The graph indexes it. A model
  summarizes code into specs (code -> spec) and edits code to match a spec
  delta (spec -> code).

### What the arch.yaml history teaches

Read with `git log --follow -- .tools/open-architecture/arch.yaml` in
`../deno-kcp` (84 commits, 641 to ~3150 lines, 309 ids).

1. **v0 (`7a95475`) guessed from prose.** A concept dictionary (`c.*`, `d.*`,
   rules with `basis: doc|inferred`, `status: built|partial|stub|gap`). No code
   anchors. Lesson: a spec not anchored to code is a guess.
2. **v1 (`85799e6`) system contexts.** Every node is
   `{id, upstream, overlay, orchestrator}` (dffml Open Architecture). Kinds are
   contexts whose upstream is their own manifest; examples are instance
   contexts whose overlay is the example manifest. Lesson: one uniform node
   shape scales; this is the CR shape.
3. **PLAN 1-5: schema, validator, evidence.** `arch.schema.json` + `validate.py`
   gate (0 errors). Refs by id must resolve. Facts cite code as `path:LINE` or
   identifiers (5.3). An attempt at a hand-written Go fact extractor (2.1) was
   reverted. Lesson: validate structure mechanically; extract facts from a real
   index (CodeGraph), not a bespoke parser.
4. **PLAN 6-25: deepening.** Reconcile graph, wake model, credentials, threat
   model (41 crossings), data model, test tiers, a 674-citation truth sweep
   (doc vs code). Lesson: drift is the steady state; drift detection must be
   automatic and continuous, which is a reconcile loop.
5. **PLAN 25: consolidation.** At 3000+ lines an `--outline` mode was needed to
   read it. Lesson: one monolithic file is the wrong storage. Split per
   context into objects (kcp CRs) and retrieve neighborhoods (graph DB).

So: **each arch.yaml system context becomes one kcp `SystemContext` object.**
Machine first keys, refs by id, every requirement cites code, a validator
gates every write, and a controller keeps `status` true to the code.

## Design

### API: `specs.publicdomainrelay.dev/v1alpha1`

All namespaced. CRDs applied into a kcp workspace (phase 1-6); APIExport +
APIBinding for multi-workspace (phase 7).

**Verified on kcp v0.33 (k8s v1.36.0):** kcp accepts
`apiextensions.k8s.io/v1` CustomResourceDefinitions inside a workspace. A CRD
applied to `root:specs` is served in that logical cluster with namespaced
scope, the `status` subresource (a write to the main resource cannot change
status; a write to `/status` cannot change spec) and `additionalPrinterColumns`
all honoured, and `kubectl api-resources --api-group=...` against
`<server>/clusters/root:specs` lists it. So phase 1-6 stay on plain CRDs;
the APIResourceSchema/APIExport/APIBinding path is only needed in phase 7 when
a second workspace must bind the same API. `deploy/install-specs.sh` is the
single place that encodes this.

`Repository` - a git working tree under management.

```yaml
spec:
  path: /abs/path/to/repo        # local working tree
  branch: main
  verify: ["go", "test", "./..."] # command that gates spec -> code
  agent: {command: deepseek-claude, args: ["-p"]}  # optional override
status:
  headCommit: <sha>
  indexedCommit: <sha>
  conditions: [Indexed]
```

`SystemContext` - one spec node (arch.yaml system context).

```yaml
spec:
  repository: <Repository name>
  upstream: <ref>                 # sc.<name> | up.<name> | self
  overlay: [<ref>]
  orchestrator: <ref>
  intent: <one paragraph, what and why>
  requirements:                   # machine first, each cites code
    - {id: r.add-two-ints, level: MUST, text: "...", codeRefs: ["function:<hex>"]}
  interfaces:                     # declared public surface
    - {name: Add, kind: function, signature: "func Add(a, b int) int", file: calc/calc.go}
  codeRefs: ["file:calc/calc.go"] # CodeGraph ids anchoring this context
status:
  observedGeneration: 3
  observedCommit: <sha>
  observed:                       # code facts from CodeGraph, deterministic
    files: [calc/calc.go]
    interfaces: [{name: Add, kind: function, signature: ..., file: ..., line: 3, codegraphId: "function:<hex>"}]
    fingerprint: <sha256 of observed facts>
  syncedCommit: <sha>             # baseline: the commit the spec was last synced against
  syncedFingerprint: <sha256>     # baseline: the fingerprint recorded at that sync
  realizedSpecHash: <sha256 of spec at last successful realize/ingest>
  conditions:
    - SpecValid      # validator passed (refs resolve, levels enum, ids unique)
    - CodeSynced     # every declared interface observed, no undeclared exported ones
    - Drifted        # observed changed since spec was last synced
```

`SpecChange` - one direction-tagged change, the unit of work and audit trail.

```yaml
spec:
  systemContext: <name>
  direction: SpecToCode | CodeToSpec
  fromSpecHash / toSpecHash       # SpecToCode
  fromCommit / toCommit           # CodeToSpec
status:
  phase: Pending | Running | Succeeded | Failed
  branch, commit, verifyExitCode, agentLog (tail), message
```

### Sync semantics (loop safety)

- spec -> code fires when `sha256(spec) != status.realizedSpecHash` and the
  change came from a human (no `specs.publicdomainrelay.dev/origin: ingest`
  annotation at that generation). Creates a `SpecChange{SpecToCode}`.
- code -> spec fires when `HEAD != status.observedCommit`. Re-extract facts
  deterministically; if `fingerprint` changed, set `Drifted=True` and create a
  `SpecChange{CodeToSpec}` that asks the model to update `intent`,
  `requirements`, `interfaces`. Writes made by ingest carry the origin
  annotation and set `realizedSpecHash`, so they never trigger spec -> code.
- One `SpecChange` Running per `SystemContext` at a time (admission).
- spec -> code works on a branch `spec/<context>/<hash8>` in a git worktree;
  `verify` must exit 0 before the commit is fast-forwarded to `branch`.
  On failure: phase Failed, branch kept, spec untouched, condition reason set.

### Graph model (HydraDB core Cypher subset only)

```
(SpecRepo {id,name,path}) -[:HAS_CONTEXT]-> (SpecContext {id,name,intent,specHash})
(SpecContext) -[:REQUIRES]-> (SpecRequirement {id,level,text})
(SpecContext) -[:DECLARES]-> (SpecInterface {id,name,kind,signature})
(SpecRequirement|SpecContext) -[:REFERENCES]-> (CodeRef {codegraph_id,kind,name,file_path})
(SpecContext) -[:UPSTREAM|OVERLAY|ORCHESTRATOR|DEPENDS_ON|INTRODUCES]-> (SpecContext)
```

Integer ids from FNV-1a of a content key (same as `pi-hydradb-clm/src/ids.ts`)
so re-ingest merges. Content keys: `repo:<name>`, `context:<name>`,
`requirement:<context>/<id>`, `interface:<context>/<name>` and
`coderef:<codegraph id>`; the last one means two spellings of the same reference
(`function:Add` and `function:<hex>`) land on one vertex. Writes use only the
upsert pattern the conformance table marks `core`. The graph is a derived index
of kcp + CodeGraph, so the merge strategy is a rebuild: delete the five managed
labels, then write every repository, context, requirement, interface and code
ref again (`specctl graph rebuild`, and the tail of `specctl ingest` when a Bolt
endpoint is configured).

### Context bundle (what the model sees)

For a context `X`: its spec YAML, its `status.observed`, the CLM context
document `.specs/context/X.md`, one-hop graph neighbors (upstream, overlay,
requirements, code refs), and `codegraph context` output for its code refs,
cut to a token budget. Same budget + managed zone idea as `pi-hydradb-clm`.

### Agents

`abc/agent` interface, two impls:

- `impl/claudecli` - shells out to `deepseek-claude -p` (configurable command)
  in the worktree. Used for both summarize (asks for JSON on stdout) and
  realize (edits files in place).
- `impl/scriptedagent` - deterministic, reads a scenario file of edits and
  spec drafts. All unit and integration tests use it. Live model tests are
  gated by `SPECD_REQUIRE_LIVE_MODEL=1`.

## Phases - each ends with running code and a runnable example

Every phase: implement, add tests, add/extend `examples/` or `Makefile`
target that demonstrates it, update `README.md`, commit, push. Then an
analysis pass reports what is left; gaps go into the next phase.

- Test: live test (skips unless kcp on PATH; `SPECD_REQUIRE_LIVE=1` fails instead) round-trips a `SystemContext` through kcp; unit tests for validator.

Done. Module is `github.com/publicdomainrelay/graph-clm-kcp-spec`; workspace is
`root:specs` on port 6447 with kine on 23797 and state in `.kcp-specd/`;
`deploy/install-specs.sh` also writes `.kcp-specd/specs.kubeconfig`, so the
example is one command, `make example-phase1` (equivalently `make kcp-up`, then

### Phase 2 - code -> facts -> kcp status + graph

- `impl/codegraphsqlite` reads nodes/edges for given files; `abc/sync`
  computes `status.observed` + fingerprint; `specctl ingest --repo` creates or
  updates `Repository` and one `SystemContext` per Go package / TS module
  (default partition: directory) with status filled and empty spec intent.
- `impl/boltgraph` + `abc/graph`: upsert contexts, interfaces, code refs.
- Example: `specctl ingest --repo fixtures/calc` then `kubectl get systemcontexts -o yaml` and `specctl graph neighbors calc`.

Done. `fixtures/calc` is a tiny Go library (the `calc` package with `Add` and
`Multiply`, their test, and a CLI over them); tests copy it to a temp dir and
commit it there, so the fixture stays a plain directory in this repository.
`specctl ingest --repo <path>` indexes the tree with `codegraph init|sync`,
reads the sqlite index with `modernc.org/sqlite`, partitions it by directory
(`calc/` -> context `calc`, `cmd/calc/` -> `cmd-calc`, root files take the
repository name; test files count as files but contribute no interfaces),
fills `status.observed` and the conditions `SpecValid`, `CodeSynced` and
`Drifted`, and sets `spec.codeRefs` to the observed `file:` refs plus the
author's non-file refs. Human fields (`intent`, `requirements`, `interfaces`,
`upstream`, `overlay`, `orchestrator`) are left alone; generated writes carry
the `origin: ingest` annotation and a `realizedSpecHash`. A second ingest
changes no spec, writes no status and reports the same fingerprint. `--bolt-url`
(env `SPECD_BOLT_URL`, `SPECD_BOLT_USER`, `SPECD_BOLT_PASSWORD`,
`SPECD_BOLT_PASSWORD_FILE`, `SPECD_BOLT_DATABASE`) makes ingest rewrite the
graph as well. `specctl graph neighbors <context>` prints one hop in and out of
a context and `specctl graph rebuild` rewrites every managed label from kcp plus
CodeGraph; both are exercised against HydraDB 7687 and ArcadeDB 7688.
`make example-phase2` is the whole example, and
`SPECD_REQUIRE_LIVE=1 go test ./... -count=1` runs the live tests: the phase 1
round trip, ingest idempotency (generation, resourceVersion and fingerprint all
unchanged on the second run) and the graph neighborhood on both backends.

### Phase 3 - arch.yaml round trip

- `specctl import-arch ../deno-kcp/.tools/open-architecture/arch.yaml` turns
  every system context (nested trees flattened, refs kept) into a
  `SystemContext` in a workspace; `specctl export --format arch` writes it back.
- Test: import -> export -> semantic diff of ids/refs/triples is empty.

Done. `abc/archyaml` is the pure model. A document is a header (every top-level
key that is not a section) plus sections; `system_contexts` is always a list,
and any other key whose value is all mappings (upstreams, orchestrators, types)
or a list of mappings that carry an id (trust_boundaries, crossings, flows,
overlays in the older revisions) is a node section too. A node is any mapping
with a string id, and it nests through upstream, overlay, orchestrator or
children. Parse flattens the tree: every node records its parent id and the slot
path it occupied (`upstream`, `overlay[3]`, `overlay[3]/upstream/field_types/x`)
and its body holds everything the node owned, with the inline children replaced
by their id refs. Export is the inverse, re-inlining each child at its slot;
`archyaml.Diff` compares two models by ids, refs, placement and preserved data,
and an empty diff is the test.

Each node becomes one `SystemContext`. The kcp name is `ArchName(id)`, a
DNS-1123 label (`sc.kind.denopod` -> `sc-kind-denopod`), and the id stays in
`spec.arch.id` (and the labels `specs.publicdomainrelay.dev/arch-id` and
`.../arch-kind`); `spec.arch` also carries the kind (`node`), the section, the
form, the position, the parent, the slot, the derived refs and the preserved
node body. One extra object (`spec.arch.kind: document`) carries the header and
the section skeleton, so even an empty section round trips. Upstreams,
orchestrators and types are therefore both preserved verbatim (inside their node
bodies, and as nodes in their own right) and queryable.

The ref vocabulary grows `ov.` and `orch.`, and a ref payload may be a
DNS-1123 subdomain, so `sc.kind.denopod` is a valid ref. `spec.RefName` still
strips the prefix for the plain vocabulary, while an arch context's refs are
resolved with `spec.ArchName`, because its dots are part of the id. `spec` also
gains `dependsOn` and `introduces`, and the graph gains the matching
`DEPENDS_ON` and `INTRODUCES` edges. `impl/archkcp` applies and reads the
objects; import is idempotent and prunes the objects under that repository that
the document no longer holds.

The three revisions (`arch.yaml`, and the same file at `85799e6` and `e77a69f`)
plus `arch.schema.json` are copied into `testdata/open-architecture/`, so the
tests do not depend on the sibling checkout. `make example-phase3` imports the
document against the live kcp, prints one hop of the graph around
`sc.deno-kcp`, exports it back and runs the live round trip test.

Two details the export normalises, both harmless under the schema: top-level
keys come out sorted (a YAML mapping has no order), and a scalar that YAML reads
as a date comes out as the quoted string of the same value, which is what
`arch.schema.json` asks for anyway. The importer also raises the kcp client's
rate limit (`--qps`, `--burst`), because client-go's default of 5 requests per
second turned a 166 object import into three minutes.

### Phase 4 - controller: conditions and drift

- `cmd/specd` + `factory/specd`: watch Repository, SystemContext and SpecChange
  (dynamic informers, with a poll fallback); re-ingest on new HEAD; set
  `SpecValid`, `CodeSynced`, `Drifted`; create `SpecChange` for both directions.
- Example: edit a fixture file, commit, watch `Drifted=True` appear.

Done. `abc/watch` is the source contract (resources in, `Added`, `Updated` and
`Deleted` out); `impl/watchinformer` holds a dynamic shared informer per
resource open against the workspace and is the default, and `impl/watchpoll`
lists every resource on a timer and turns the difference between two listings
into the same events, as the fallback for an API server whose watch a client
cannot hold. `factory/specd` wires the source, a workqueue and the three
reconcilers; only `cmd/specd` installs signal handlers, and SIGINT or SIGTERM
drains the workers and stops the watches.

`Repository` reconcile reads the git HEAD of `spec.path` and runs the phase 2
ingest when it differs from `status.indexedCommit`. A commit is invisible to the
API server, so each Repository requeues itself every `--resync` (5s default);
that timer, not the watch, is what notices new code. A tree whose HEAD cannot be
read gets `Indexed=False` with `HeadUnavailable` rather than an error loop, and
the ingest failure itself is the only thing that backs off.

`SystemContext` reconcile indexes nothing. It turns the stored facts into the
three conditions through the same pure deciders ingest uses
(`abc/sync.Decide`/`abc/sync.Conditions`, so the two writers can never disagree
and ping-pong), records `observedGeneration`, and raises the work.
`CodeSynced` grows the requirement code refs: a ref that names neither an
observed file nor an observed interface unsyncs the context.

Two status fields joined the CRD: `syncedFingerprint` and `syncedCommit`, the
baseline the spec was last brought into agreement with. Ingest establishes them
on the first ingest of a context and never moves them afterwards, so a context
that drifted stays drifted when a later commit elsewhere re-ingests the same
tree; the baseline moves when the drift is worked off in phase 6. `Drifted` is
therefore `syncedFingerprint != observed.fingerprint`, which is what the plan's
"the fingerprint recorded when the spec was last synced" means.

A `CodeToSpec` change is due while the context is drifted and `syncedCommit` and
`observedCommit` are a usable pair, and a `SpecToCode` change is due when the
spec no longer hashes to `status.realizedSpecHash`. The plan says "on the
Drifted transition", and that edge is not observable: ingest computes the
conditions and stores them in the same status write that stores the new
fingerprint, so the controller only ever sees the post-transition state. One
change per drift episode comes from the other half of the rule instead: a change
of a direction is only created when nothing of that direction is still `Pending`
or `Running` for the context, which is also what makes a controller restart
safe. Names are deterministic (`<context>-c2s-<from8>-<to8>`,
`<context>-s2c-<to8>`) and creation is a create-if-absent, so an already
existing change is never rewritten back to `Pending`.

Ingest's `realizedSpecHash` rule is what keeps a human edit visible. It moves
the hash only when the stored spec already hashed to the previous realized hash,
so an ingest that runs after a human edit does not absorb it; the edit stays
`hash != realizedSpecHash` and the controller raises the `SpecToCode` change.
An ingest that finds nothing pending absorbs its own write, which is what keeps
a freshly applied or freshly ingested context from looking like an edit.

`SpecChange` reconcile keeps a change `Pending` and enforces admission: at most
one `Running` change per SystemContext, the lowest name wins, and a loser is
marked `Failed`. Nothing sets `Running` until phases 5 and 6. Because a create
cannot write the status subresource, the creator patches the phase in right
after the create, so no reader ever sees a change without one. An episode that
failed is retried as a new record (`<base>-a2`, `<base>-a3`, ...) rather than
being dropped by its own name colliding with the failed attempt; a cap and a
backoff for repeated failures belong with the agents in phases 5 and 6.

Four things the implementation has to get right that the sketch does not name,
each of which the live run or a review found:

- A SystemContext belongs to exactly one Repository, so ingest refuses a
  partition whose name is already owned by another one (`spec.repository` is
  set and differs) and reports it as skipped. Two trees that both hold a
  directory named `calc` would otherwise take turns writing one context.
- The graph rebuild deletes every managed vertex and writes them again, so it
  is serialized inside `impl/ingest`; a controller with several workers can
  finish two ingests at the same moment.
- An informer delete can arrive as a tombstone, so the watch unwraps it with
  the deletion-aware key function.
- A Repository whose HEAD already matches `status.indexedCommit` still writes
  the `Indexed` condition, so a condition left `False` by an earlier failure
  (a path that did not exist yet) comes back to `True`.

`fixtures/greet` is the second fixture and the first that is not Go: a Deno
TypeScript module with a root `mod.ts`, a `mod_test.ts`, a `deno.json` and a
second directory `format/`, so the directory partition and the interface
extraction are proved on exported functions, an exported interface and an
exported class. `abc/sync.IsTestFile` learned Deno's `_test.ts` convention so
those test files stay in `observed.files` and contribute no interfaces.

`make example-phase4` is the whole example (a temporary copy of `fixtures/calc`,
a commit that adds `Subtract`, the drift condition, the two changes, a four
second quiet window, SIGTERM). `SPECD_REQUIRE_LIVE=1 go test ./... -count=1`
covers the controller end to end against the live kcp, including the
TypeScript fixture.

### Phase 5 - code -> spec with a model (CLM)

- `abc/agent` + `impl/claudecli` + `impl/scriptedagent`; context bundle
  builder; `CodeToSpec` SpecChange reconciler writes intent/requirements/
  interfaces with origin annotation; context doc `.specs/context/X.md`.
- Example: `specctl ingest --summarize` on a fixture fills specs.

Done. `abc/agent` is the pure half of the loop, so the loop is testable
without a model. `ContextBundle` is what one context looks like to a model: the
spec, `status.observed`, the model zone of the context document, one hop of the
spec graph in both directions, the `codegraph context` and `codegraph node`
excerpts behind its code refs, and a token budget. `Fit` keeps whole sections in
priority order and names the ones it dropped; a section is never cut in half.
`ParseDraft` reads the answer strictly: a fenced or prose-wrapped object is
tolerated, an unknown level, a duplicate id, an empty requirement or a missing
intent is an error, and a code ref the observed facts do not answer to is
dropped and reported. A model that writes a bare name (`Add`) is read as the
interface of that name and stored as its canonical CodeGraph id, so a model
ref and a human ref that mean the same symbol land on the same vertex; that
normalisation is what made the live model pass, since the first real answer
used bare names and the validator refuses them.

`impl/bundle` builds that bundle from kcp plus `impl/boltgraph` plus
`impl/codegraphcli`, and owns `<repo>/.specs/context/<name>.md`: the model zone
above `<!-- SPECD_MANAGED_BEGIN -->` and the resolved code refs below it,
regenerated from the observed facts on every summarize, exactly the
`pi-hydradb-clm` pattern with specd's own markers. The graph and codegraph
reads are optional and a codegraph that cannot read one symbol is skipped, so a
bundle is never lost to a missing excerpt.

`impl/claudecli` is the model agent: a configurable command (default
`deepseek-claude -p --output-format text`), the prompt on **standard input**
because the launcher word splits its argv, `cwd` the repository under
management, a timeout, and the stderr tail in the error. `impl/scriptedagent`
answers from a YAML or JSON scenario file, drafts keyed by context name and
realize steps as writes, patches and deletes; its drafts go through the same
strict parser a model answer does, so a scenario cannot draft what a model
could not. All non-live tests use it. `impl/agentfactory` turns one option
string into an agent, so `specd` and `specctl` agree on what
`--agent scripted:<file>` means.

`impl/summarize` is one code -> spec unit of work and both the controller and
the CLI call it: build the bundle, ask the agent, validate the draft with the
same validator a human edit passes, write the spec with the `origin: ingest`
annotation and the realized hash of what it wrote, move the synced baseline to
the observed facts so `Drifted` goes False, and write the context document. A
second run over the same facts changes nothing.

The `SpecChange{CodeToSpec}` reconciler takes a change from `Pending` to
`Running`, summarizes, and records `Succeeded` or `Failed` with the agent
output tail. A controller started without an agent leaves every change
`Pending` for a human, which is what keeps `make example-phase4` meaning what
it means. Agent selection is `--agent claude|scripted:<file>` at the controller
and `Repository.spec.agent` per repository, the repository winning.

Two things the phase 4 sketch did not name, both found by the live run:

- The plan already said spec -> code fires only when the spec edit "came from a
  human". Phase 4 approximated that with `sha256(spec) != realizedSpecHash`, and
  the approximation breaks the moment an agent writes a spec: the spec update
  and the status update that acknowledges it are two API calls, and a reconcile
  that runs between them reads the new spec against the old realized hash and
  calls the tool's own write a human edit. The object now carries
  `specs.publicdomainrelay.dev/origin-hash`, the hash of the spec the tool
  wrote, in the same call as the spec; `SpecEditDue` reads that and a write
  that still hashes to it is not an edit. The annotation survives a human
  apply, so it cannot be used to smuggle an edit past the controller: a human
  changes the spec and the hash no longer matches.
- A drift episode is keyed by the commit pair, so once one of its changes has
  succeeded the episode is over and the creator raises no further attempt for
  it, even if the status that records the success has not landed yet. Without
  that rule the same two-call window produced a second, pointless attempt that
  wrote nothing.

A failed episode is retried as a new record with a backoff that doubles —
`--retry-backoff`, then twice that, and so on — and stops for good after
`--max-attempts` (3 by default). The cap lives in the creator and again in the
reconciler, so a change created by hand cannot outrun it. A failed change asks
for its SystemContext again, which is what drives the retry: a code base that
is not changing produces no other event.

`specctl ingest --summarize --agent <kind>` fills the spec of every context
whose intent is still empty. It runs the summarize directly rather than
creating `CodeToSpec` changes, so the CLI works without a controller running;
the audit trail for the controller path is the SpecChange, and the two writers
are the same `impl/summarize` call, so the result is identical.

The live model test is gated by `SPECD_REQUIRE_LIVE_MODEL=1` (a model is slow,
costs money and is not deterministic) and is the only test that runs
`deepseek-claude`. It summarizes `fixtures/calc` and asserts the answer parses,
validates and names `Add` and `Multiply`; it runs in about ten seconds.

`make example-phase5` is the whole controller example: a temporary copy of
`fixtures/calc`, a scripted agent, a commit that adds `Subtract`, and a check
that one change succeeded, the spec carries the agent's intent and interfaces,
`Drifted` went False and no `SpecToCode` change appeared. The same target shows
`specctl ingest --summarize` filling an empty spec. The review gaps that phase 4
left are closed too: `abc/watch`, `impl/watchinformer` (against a fake API
server that speaks the streaming list, bookmark included) and `cmd/specd`'s
flag and config wiring all have unit tests now.

### Phase 6 - spec -> code, driven by a structured delta

Manifests must delta cleanly. That is the core requirement of the format.

- Every list in every CRD is a keyed list: `x-kubernetes-list-type: map` with
  `x-kubernetes-list-map-keys` (`requirements` by `id`, `interfaces` and the
  observed interfaces by `name`, `conditions` by `type`) and
  `x-kubernetes-list-type: set` for `codeRefs`, `overlay`, `dependsOn` and
  `introduces`. Server side apply then edits one entry without rewriting the
  list.
- The last realized spec is kept as a snapshot (`status.realizedSpec`), so a
  delta is always computable from kcp alone.
- `abc/delta` (pure): `Diff(old, new) Delta` per keyed entry: added, removed,
  changed (field level), for intent, requirements, interfaces, codeRefs,
  upstream/overlay/orchestrator. `Apply(spec, Delta)` is its inverse; property
  test: `Apply(old, Diff(old, new)) == new`.
- `SpecChange.spec.delta` carries that structured delta in both directions:
  `SpecToCode` (human or CLM spec edit) and `CodeToSpec` (observed fact delta
  from `status.observed` old vs new). The agent receives the delta plus the
  bundle, never "here is the whole spec, guess what changed".
- `impl/gitrepo` worktrees; `SpecToCode` reconciler: build bundle + delta, run
  agent in worktree, run `verify`, commit, merge, re-ingest, `CodeSynced=True`.
- Example: `kubectl patch systemcontext calc --type merge -p '{"spec":{"interfaces":[... Subtract ...]}}'`
  then `kubectl get specchange -o yaml` shows a one entry delta and
  `git -C <repo> log` shows the agent commit with tests passing.

Done. The list types are in `deploy/crds/`: `requirements` by `id`,
`interfaces` by `name`, `observed.interfaces` and `syncedObserved.interfaces`
by `name`, `conditions` by `type` are list maps, and `codeRefs`, `overlay`,
`dependsOn` and `introduces` are sets, in `spec`, in `status.realizedSpec` and
in the delta. Verified live: one manager server-side-applies a patch that names
one requirement and one interface, and the other entries, the intent and the
code refs set are exactly as they were.

The wire form of the delta lives in `abc/spec` (a `SpecChange` carries one) and
the pure algebra in `abc/delta`: `Diff`/`Apply` for specs, `DiffObserved`/
`ApplyObserved` for fact sets, and `Summary` for the compact form `specctl get
specchange` prints as a `+2 ~1 -1` tally. The JSON is the contract phase 8
mirrors in TypeScript, so it is pinned by golden files in `testdata/delta/`
(regenerate with `SPECD_UPDATE_GOLDEN=1 go test ./abc/delta`). `Apply(old,
Diff(old, new)) == new` is a property test over 500 generated specs as well as
a table test.

The keyed lists have no order, so the spec hash is taken over a canonical form
(`spec.Canonicalize`: requirements by id, interfaces by name, sets sorted and
deduplicated). Reordering a list in a manifest is therefore not an edit, and two
spellings of the same spec raise no work. `spec.SameDeclaredState` is the same
idea for the fields a human owns, ignoring the code refs ingest derives from the
tree.

`impl/realize` is one spec -> code unit of work and both the controller and a
CLI caller go through it: a worktree on `spec/<context>/<hash8>` off the managed
branch, the agent editing it, `Repository.spec.verify` run there, a commit
signed `specd <specd@localhost>` that stages everything except the codegraph
index, a `--ff-only` land onto the managed branch, and an ingest that adopts the
result. The commit message is `realize <context>: <delta summary>`, and
`status.filesTouched` is the diff stat of the commit.

The adopt is what makes the loop safe, and it took a live run to find. Ingest
after a realize would otherwise compute the new observed facts against the old
`syncedFingerprint` and report the tool's own work as drift, which raises the
opposite change; and because the ingest itself adds the new file to
`spec.codeRefs`, the realized hash has to be taken after that merge, not before.
`ingest.Options.Adopt` carries the spec that was realized and moves the synced
baseline, the realized hash and the `realizedSpec` snapshot onto what it just
read, in the one status write it already makes. A second window is temporal: the
Repository resync can index the branch between the fast-forward and that ingest,
so the Repository reconciler now waits while a spec -> code change is `Running`
(only that direction moves the branch, so a running code -> spec change does not
need the index to stand still). Both are covered by the phase 6 live test, which
asserts that one spec edit produces exactly one change.

`SpecChange.spec.delta` is filled by the creator in both directions:
`delta.Diff(status.realizedSpec, spec)` for `SpecToCode` and
`delta.DiffObserved(status.syncedObserved, status.observed)` for `CodeToSpec`,
with `status.realizedSpec` and `status.syncedObserved` as the snapshots that
make both computable from kcp alone. A change created before phase 6 has no
delta and the reconciler recomputes one.

The realize ask puts the delta first, then the spec the code must reach, then
the verify command, and the rule *edit files only, do not commit*, because the
reconciler owns the worktree and the commit. `impl/claudecli.Realize` runs it in
the worktree; `impl/scriptedagent.Realize` applies the scenario's write, patch
and delete steps. A failed verify leaves the change `Failed` with the exit code,
the output and the files it touched, keeps the branch, leaves the managed branch
and the spec untouched, and hands the verify output to the next attempt as its
instruction; attempts back off and stop after `--max-attempts`.

`Repository.spec.agent.kind` selects the agent per repository (`claude` or
`scripted:<file>`; `pi` is named and refused until phase 8), and it wins over
the controller's `--agent`, closing the review gap phase 5 left. A repository
that names an agent makes a controller started with no `--agent` work the
changes off.

`make example-phase6` is the whole example: a temporary copy of `fixtures/calc`,
a `Repository` that names its own scripted agent, specd with no `--agent`, a
server side apply that adds one interface and one requirement, the two entry
delta, the worktree branch, the agent commit, the verify exit code, the files
touched, `CodeSynced=True` and `Drifted=False`. `make example-phase6-failing`
runs the same with a scenario whose Subtract cannot pass, and
`SPECD_REQUIRE_LIVE=1 go test ./... -count=1` covers the keyed list behaviour,
the realize loop and the failed verify against the live workspace. The live
model test is gated by `SPECD_REQUIRE_LIVE_MODEL=1` and takes about fifteen
seconds.

`deploy/install-specs.sh` retries the CRD apply until the API group is served,
because a cold start can have the workspace Ready while the cluster is still
bringing up apiextensions; proved from a cold start (`deploy/stop-kcp.sh`, `rm
-rf .kcp-specd`, `make test-live`).

`make demo` is the first end to end run of phases 1 to 6 against one cluster.

### Phase 7 - one manifest populates an unknown codebase

A new, unknown codebase must become manifests from one declarative object.
`Repository` is that trigger manifest.

- `Repository.spec.source`: `{path}` or `{git: {url, ref}}`; specd clones into
  a managed cache dir.
- `Repository.spec.populate`: `{partition: directory|package, include, exclude,
  summarize: bool, agent}`.
- specd on a new or changed `Repository`: clone/fetch, `codegraph init|sync`,
  create one `SystemContext` per partition (status observed), then one
  `CodeToSpec` change per context when `summarize` is true, admission-limited.
  `Repository.status.phase`: `Cloning -> Indexing -> Populating -> Populated`
  (or `Failed`), with counts of contexts total/summarized/failed.
- `specctl ingest` stays as a thin wrapper that applies a `Repository` and
  waits, so there is one code path.
- Example: `kubectl apply -f examples/populate/repository.yaml` pointing at a
  fixture git url, then `kubectl get systemcontexts` fills with summarized
  specs without any other command.

### Phase 8 - the CLM graph extension is the live sync path

kcp is the only state engine. The graph is a derived index. The
`pi-hydradb-clm` extension becomes a first class writer and reader of kcp
state, so a model working in a session updates specs as it learns.

- One context file per `SystemContext` (`.specs/context/<name>.md`, the file
  phase 5 already writes). Model zone mirrors `spec` (intent, requirements,
  interfaces as a fenced machine block); managed zone renders `status` and
  resolved CodeGraph refs.
- Extension, `session_start` / `context` hooks: read the `SystemContext` from
  kcp (kube REST with the workspace kubeconfig), render the file.
- Extension, `turn_end` and `hydradb_remember`: parse the model zone, compute
  the delta against the kcp spec (same delta shape as `abc/delta`, TS mirror
  with a shared JSON golden test), PATCH kcp with annotation
  `specs.publicdomainrelay.dev/origin: clm`. specd treats that as a spec edit
  and opens a `SpecToCode` change carrying the delta. A remembered concept
  with `code_refs` becomes a requirement with `codeRefs`.
- Graph ids are shared: both sides use FNV-1a content ids and CodeGraph ids,
  so `Pi*` nodes and `Spec*` nodes join on `CodeRef.codegraph_id`; add a
  `(PiMemory)-[:SPECIFIES]->(SpecRequirement)` edge.
- `impl/piagent`: a third `Agent` that runs pi with the extension loaded, so
  realize work also flows through the same context file and back into kcp.
- Example: run pi on a fixture with `HYDRA_CLM_KCP_KUBECONFIG` set, ask it to
  add a requirement; watch the `SystemContext` spec change, a `SpecToCode`
  change open with a one entry delta, and the code commit land.

### Phase 9 - multi-workspace and git-native specs

- APIExport/APIBinding so tenant workspaces bind the spec API; controller
  watches through the virtual workspace (kcp-libs `factory/controller`).
- `.specs/*.yaml` in the managed repo mirrors kcp both ways (`specctl sync`),
  so a PR carries spec and code together.

### Phase 10 - fixtures and effectiveness

- `fixtures/`: at least three small repos (Go library, Go HTTP service, TS/Deno
  module) each with tests, plus `scenarios/*.yaml`: a spec edit and hidden
  acceptance tests.
- `specctl eval` measures:
  - code -> spec: interface recall (declared vs exported symbols), requirement
    anchoring (share of requirements with resolving code refs), validator pass.
  - spec -> code: share of scenarios where verify + hidden acceptance tests
    pass, number of agent attempts, files touched outside the context's files.
  - round trip: ingest -> summarize -> regenerate spec -> diff stability.
  - populate: one `Repository` manifest on an unseen fixture reaches
    `Populated`; share of partitions with a validated spec; wall time.
  - delta precision: for each scenario, the `SpecChange.spec.delta` entry count
    equals the scenario's intended edit count, and the agent's commit touches
    only files of contexts named in the delta.
  - CLM path: scenarios driven through the pi extension instead of a kubectl
    patch reach the same pass rate.
- Scripted agent gives a deterministic baseline; a live run with
  `deepseek-claude` writes `docs/eval/run-<date>.md`.

### Done means

`make demo` on a clean machine with kcp, kine, kubectl, codegraph, go and a
HydraDB on PATH: starts kcp, starts specd, applies one `Repository` manifest
for an unseen fixture and waits for `Populated`, applies a spec edit (kubectl
and via the pi CLM extension), shows the one entry delta, the agent commit with
passing tests, and prints the eval table. `make check test` green. Docs say how and why.
